NREL Phase VI (Sequence S) blade and S809 polar, exported to QBlade CE for
manual cross-validation against this project's own BEM solver
(`src/bem/rotor.py`, `solve_rotor`). Generated by
`src/validation/export_qblade.py`;
see the 2026-07-26 journal entries for how the underlying S809 polar cache was
corrected and how this export's extrapolation was derived and verified.

**Caveat on the QBlade steps below**: the exact menu wording/paths are from
QBlade's documented workflow, not verified click-by-click against QBlade CE
2.0.9.7's UI on this machine — the shape of each step is right, but confirm
menu labels against your installed version if something doesn't match.

## Why two Reynolds numbers

`solve_rotor` normally estimates a *per-station* Reynolds number from the
local chord and relative velocity and interpolates the real XFOIL cache
continuously in Re. QBlade's `.plr` format is a single fixed Re per polar
object, so both `.bld` files pin every station to one Re instead, to keep the
two solvers looking at the identical 2D Cl/Cd/Cm curve.

At the operating point below, this project's solver estimates a per-station
Reynolds range of **577,000 - 945,000** -- all of which clamp to the cached
Re=500,000 ceiling. So the **Re=500k pair is the physically meaningful one**:
it reproduces `solve_rotor`'s own default (continuous per-station Re)
behaviour exactly, and is what should be compared against QBlade's own BEM
run for a real check. The Re=100k pair is kept only because it was the
original comparison point and is cheap to keep in step.

## Operating point (Sequence S)

Set these identically in both solvers:

| Parameter | Value |
|---|---|
| Freestream wind speed | 7.0 m/s |
| Rotor speed | 71.63 RPM (`PHASE_VI_RATED_RPM`) |
| Collective (tip) pitch | 3.0 deg |
| Air density | 1.225 kg/m^3 |
| Number of blades | 2 |
| Rotor radius | 5.029 m |
| Hub radius | 0.508 m |
| -> Tip-speed ratio | 5.389 |

| Re pinned | Cp | Ct |
|---|---|---|
| 100,000 | 0.2887 | 0.4761 |
| **500,000 (physically meaningful)** | **0.3571** | **0.5321** |

## Workflow 1 -- direct blade + polar import (my polars, QBlade's BEM)

Confirms the two BEM *solvers* agree given identical aerodynamic input.

1. QBlade: Rotor Blade Design module -> File > Import Blade Geometry ->
   `phase_vi_blade_Re500k.bld` (or `phase_vi_blade.bld` for the Re=100k pair).
   This pulls in `S809_Re500k.plr` (or `S809.plr`) automatically via the
   `POLAR_FILE` column, so no separate polar import is needed here.
2. Simulation module -> BEM simulation -> set V=7.0 m/s, RPM=71.63, pitch=3.0
   deg, air density=1.225, 2 blades -- matching the table above.
3. Run the steady BEM simulation, export per-station Cl/Cd/alpha/a/a' and
   rotor Cp/Ct.
4. Diff against `bem_solver_phase_vi_result_Re500000.csv` (or `_Re100000.csv`)
   and the Cp/Ct table above. Any disagreement here is about solver mechanics
   (induction/tip-loss treatment, root-finding, Viterna extrapolation used
   past the XFOIL band) since both solvers are reading the same polar curve.

## Workflow 2 -- bare airfoil import (QBlade's own XFOIL, compare polars)

Confirms the underlying 2D aerodynamic data agrees before trusting a BEM
comparison built on top of it.

1. QBlade: Airfoil Design module -> File > Import Airfoil ->
   `data/airfoils/s809_qblade.dat` (do **not** import a `.plr` here -- the
   point is to have QBlade compute its own polar from the raw shape).
2. Direct (XFOIL) Analysis tab -> Reynolds numbers 100000, 150000, 200000,
   300000, 400000, 500000, Mach 0.
3. Ncrit is the setting that matters most here. Two runs worth doing:
   - **Ncrit=5**, to match this cache exactly (`_DEFAULT_NCRIT` in
     `src/xfoil/build_polar_cache.py`) -- the fairest apples-to-apples check.
   - **Ncrit=9** (QBlade's XFOIL default), as an independent sanity check on
     the 2026-07-26 finding: the S809's 21%-thickness laminar separation
     bubble made our own XFOIL 6.99 produce a non-physical polar at Re<=150k
     under Ncrit=9 (Cl collapsing to negative at +3 deg incidence). If
     QBlade's bundled XFOIL shows the same collapse at Ncrit=9, that is
     strong independent confirmation the problem was the physics setup, not
     this project's wrapper -- which is exactly what the corrupted
     `S809.plr` this replaced also showed (see the 2026-07-25/26 journal
     entries).
4. Compare QBlade's computed Cl/Cd/Cm vs alpha against
   `data/polars/s809/S809_Re<N>.csv` for the matching Re.

## Workflow 3 -- polar extrapolation (QBlade's Viterna/Montgomerie, compare to mine)

1. In QBlade's polar view, select the polar(s) from Workflow 2 and use the
   "Create 360 deg Polar" / extrapolation tool (Viterna-Corrigan or
   Montgomerie-Ostowari, whichever QBlade offers) with Cd_max = 1.8 to match
   this project's convention.
2. Compare the extrapolated curve against `S809_Re500k.plr` /
   `S809.plr` beyond the XFOIL-converged band (+18 deg out to 90 deg is the
   region that matters for a wind turbine; the two should agree closely there
   since both use the same classical Viterna form -- see
   `src/validation/export_qblade.py`'s `build_full_range_polar` docstring for the exact
   coefficients and the negative-alpha/reversed-flow conventions it uses,
   which are less standardized and more likely to diverge from QBlade's own
   choices).

## Workflow 4 -- blade with QBlade's own polar (round-trip BEM comparison)

1. Build (or edit) a blade in QBlade's Rotor Blade Design module using the
   same station table as `phase_vi_blade_Re500k.bld` (r, chord, twist columns
   above), but pointing every station at QBlade's own extrapolated polar from
   Workflow 3 instead of `S809_Re500k.plr`.
2. Run the same BEM simulation as Workflow 1 (same V, RPM, pitch).
3. Compare Cp/Ct against `bem_solver_phase_vi_result_Re500000.csv` again. This
   isolates how much of any remaining discrepancy comes from the polar itself
   (XFOIL settings + extrapolation choice) versus the BEM solver mechanics
   already checked in Workflow 1.

## Post-stall asymmetry: resolved 2026-09-10

There used to be one here, recorded as a caveat on every workflow below.
`bem.airfoil.S809Polar` *clamped* alpha to the cached [-8, 18] deg band rather
than extrapolating past it, while the `.plr` files hand QBlade a full Viterna
extrapolation -- so past stall the two solvers were reading different polars,
not the same polar through different code.

Work order Task 4 deleted that clamp. `polars.polar.CachedPolar` reads the
+/-180 deg cache the `.plr` files were exported from, so the two solvers now
share a post-stall model as well as a measured band, and a TSR sweep that
pushes stations into stall is a fair comparison rather than a caveated one.

At the Sequence S operating point documented here every station sits at
alpha 3.5-11 deg, well inside the converged band, so Workflows 1 and 4 were
never affected either way. What did change at this point is second-order and
worth knowing about when re-running them: the interpolation scheme moved from
bilinear to cubic-in-alpha (Task 3), which shifts Cd by up to 4 % at Re = 100k
where Cd's curvature is highest. `bem_solver_phase_vi_result_Re*.csv` were
regenerated for both effects in the same commit as the golden snapshot; see
`tests/golden/README.md`'s 2026-09-10 change-log entry.
